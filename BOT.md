Единственный источник правды о боте. Читать ПЕРЕД работой с кодом или схемами.

## 0. Коротко

- Сервер: Minecraft **1.12.2**, Forge **14.23.5.2860**, моды **Applied Energistics 2** (rv6-stable-7) и **IndustrialCraft 2** (2.8.222-ex112). Offline-mode, пароль не нужен.
- **На нашем сервере режим `index.js` (mineflayer) НЕ РАБОТАЕТ: mineflayer не разбирает чанки модовой сборки.** Код оставлен в репозитории, но не использовать. Любые задачи, требующие модели мира (чтение блоков, рельефа), через mineflayer не решаются. Подробности и альтернатива — §5, §10.1, §11.
- В проекте **два независимых режима**:
  - **`index-cmd.js` — основной и единственный рабочий режим.** «Сырой» клиент без модели мира (`minecraft-protocol`, без mineflayer). Превращает JSON-схему в команды `/fill` и `/setblock` и шлёт их в чат от имени бота. Боту нужны **права оператора (OP)**. Быстро, умеет поворот, расчистку, основание, продолжение после разрыва. Все большие постройки (АЭС, Останкино) — этим режимом.
  - **`index.js` — бот «в мире» (mineflayer). НЕ РАБОТАЕТ на этом сервере** (см. выше) — ходит и ставит блоки руками по одному, слушает команды в чате (`!goto`, `!place`, `!build`, `!stop`); даже если бы работал, для строительства города не годится (медленно, ориентацию не соблюдает, модовые блоки не знает), см. §5.
- Схема = JSON-массив `{ "x", "y", "z", "block" }`, координаты относительные, `block` = `"имя"` или `"имя:metadata"`. См. §6.

Скопировать `.env.example` → `.env`:

| Переменная | Обязательна | По умолчанию | Смысл |
|---|---|---|---|

| `MC_USERNAME` | нет | `Builder` | ник бота (offline-mode) |
| `MC_VERSION` | нет | `1.12.2` | только для логов; реальная версия всегда определяется автоматически |

### 3.2 `config.js` (поведенческие настройки, в git)

| Ключ | Значение | Где используется |
|---|---|---|
| `commandPrefix` | `!` | префикс чат-команд (index.js) |
| `placeDelayMs` | 1200 | пауза между блоками при `!build` (index.js) |
| `reconnectDelayMs` | 5000 | пауза перед переподключением (index.js) |
| `gotoRangeBlocks` | 1 | «дошёл», если в пределах N блоков; для установки блоков используется N+3 |
| `schemasDir` | `./schemas` | папка схем (оба режима) |
| `commandsPerSecond` | 5 | троттлинг команд (index-cmd.js) |
| `maxFillVolume` | 4096 | макс. объём одного `/fill` для схем, расчистки и основания (протокольный лимит 32768; 4096 взято как предосторожность на случай, что большие `/fill` подвешивают модовый сервер — **это не проверено и не измерено**, см. §10.5.2 «Опыт») |
| `tpRenderRadiusBlocks` | 128 | радиус «дальности прорисовки» от точки телепорта до края (index-cmd.js) — см. §4.7 |
| `tpChunkLoadWaitMs` | 5000 | пауза после подтверждённого `/tp` на догрузку чанков (index-cmd.js) — см. §4.7 |

### 3.3 Подключение (общее для обоих режимов)

Всегда `version: false` + `autoVersionForge(client)`: клиент сначала делает server list ping, получает список модов, затем проходит Forge-рукопожатие с точным списком. `auth: 'offline'`. Версия становится известна только на событии `login`.

## 4. Режим A — `index-cmd.js` (основной)

### 4.1 Запуск

```
node index-cmd.js СХЕМА.json X Y Z [--prepare] [--foundation-to=Y] [--foundation-material=stone[:meta]] [--rotate=0|90|180|270]
node index-cmd.js --wipe X1 Y1 Z1 X2 Y2 Z2 [--ground=Y]
node index-cmd.js --retry logs/failed-<label>-<время>.txt
node index-cmd.js            (без аргументов — тестовый режим)
```

- `X Y Z` — **origin**: абсолютная точка, в которую попадает локальная `(0,0,0)` схемы. Для обычных схем это угол с минимальными X, Y, Z.
- `--prepare` — перед постройкой залить воздухом габарит схемы **+1 блок по бокам (X/Z) и +3 сверху**, снизу без запаса.
- `--foundation-to=Y` — работает **только вместе с `--prepare`**. Заливает основание под следом схемы (без запаса по бокам) от `originY−1` вниз до `Y` включительно. Если `Y > originY−1`, основание не строится.
- `--foundation-material` — материал основания, по умолчанию `stone`.
- `--rotate` — поворот по часовой стрелке (вид сверху), см. §7. Недопустимое значение — немедленная ошибка.
- `--wipe` — режим зачистки, несовместим со схемой. Бокс по двум углам (порядок любой). Без `--ground` — всё воздухом. С `--ground=Y` — всё **строго ниже Y** заливается `stone`, от Y и выше — воздухом. Боксы режутся по 32768 (не по `maxFillVolume`).
- `--retry <файл>` — повторно шлёт команды из текстового файла (одна на строку — формат `logs/failed-*.txt`, см. §4.7), той же логикой телепорта и учёта ответов. Несовместим со схемой и `--wipe`.
- Без аргументов — тест: держит соединение 60 с и шлёт `/setblock 61 72 242 minecraft:stone` (координаты захардкожены).

Ошибки в файле схемы, `--rotate`, `--wipe` и `--retry` проверяются **до** подключения: процесс сразу завершается с кодом 1 и понятным сообщением. Кривые координаты схемы (не числа) — молча уходит в тестовый режим.

### 4.2 Конвейер

1. Разбор CLI → загрузка и валидация схемы (§6.3).
2. Поворот (`rotateSchema`), если задан; в лог — габарит до/после.
3. Сборка **полного списка команд один раз**, в таком порядке:
   1. расчистка (`--prepare`) — боксы `air`;
   2. основание (`--foundation-to`);
   3. «твёрдые» блоки схемы — жадное схлопывание в параллелепипеды, **отсортированные по нижней Y бокса (снизу вверх)** (§4.3);
   4. «крепящиеся» блоки (кроме воды/лавы) — по одному `/setblock` в порядке файла (§4.4);
   5. вода/лава — отдельным финальным проходом, тоже схлопнуты в боксы и отсортированы снизу вверх, как п.3 (§4.4).
4. Подключение, ожидание готовности (первый пакет `position` или `update_health` с health > 0), пауза 1 с.
5. `/gamemode 3` и телепорт на площадку зона за зоной (подробно — §4.7): без этого команды могут уйти в незагруженные чанки и не встать.
6. Отправка через очередь: не чаще `commandsPerSecond` (5/с). Команды длиннее 256 символов не отправляются (пишется в лог). Каждый ответ сервера сопоставляется с отправленной командой (§4.7) — успех/без изменений/ошибка.
7. После последней команды — ждёт ответов ещё до 10 с, печатает сводку (успешно/без изменений/ошибок) и отключается сам, `exit 0`. Команды с ошибками (и без ответа вовсе) — в `logs/failed-<label>-<время>.txt`.

Формат команд: `/fill x1 y1 z1 x2 y2 z2 имя meta` и `/setblock x y z имя meta` (режим замены по умолчанию — `replace`, т.е. перезаписывается всё, что было).

### 4.3 Схлопывание в боксы (`buildBoxes`, `buildSortedBoxCommands`)

Для каждой клетки в порядке файла, ещё не вошедшей в бокс: расширение по X, затем по Z (весь X-отрезок того же типа), затем по Y (весь X×Z прямоугольник того же типа). «Тип» = имя + metadata. Боксы больше `maxFillVolume` режутся пополам по самой длинной стороне. Бокс 1×1×1 превращается в `/setblock`.

Алгоритм жадный, не оптимальный. **Итоговые боксы сортируются по нижней Y (`y1`) по возрастанию** — стабильно (`Array.prototype.sort` в Node.js/V8 гарантированно стабилен с ES2019, при равной `y1` порядок как в исходном файле). Раньше сортировки не было (порядок — по первой клетке в файле, не по высоте) — это и было причиной падения песка без опоры (см. §10.4.8 «Опыт», §11 — пункт про это исправлен). Применяется к обеим группам боксов — твёрдым (§4.2 п.3) и воде/лаве (§4.4, финальный проход п.5) — независимо друг от друга.

### 4.4 «Крепящиеся» блоки (`ATTACHED_BLOCK_NAMES`) и вода/лава (`LIQUID_BLOCK_NAMES`)

Крепящиеся идут отдельным проходом после всех твёрдых, по одному `/setblock`, в порядке файла:
`torch`, `wooden_door`, `ladder`, `lever`, `stone_button`, `wooden_button`, `sign`, `rail`, `vine`, `stone_pressure_plate`, `wooden_pressure_plate`, `tripwire_hook`, а также всё, что оканчивается на `_door` или `_torch`. Префикс `minecraft:` отбрасывается при проверке.

**Вода/лава (`water`, `lava`, `flowing_water`, `flowing_lava`) сюда больше не входят** — раньше они были в этом же списке и лились по одному `/setblock` на блок (для схем с большими объёмами воды это было на порядок медленнее — см. §4.6). Теперь они схлопываются в боксы тем же `buildBoxes`, режутся по `maxFillVolume` и сортируются снизу вверх (§4.3), как твёрдые, но идут **отдельным финальным проходом после крепящихся** (§4.2 п.5) — чтобы борта (стены, дно) и любые крепящиеся блоки внутри ёмкости уже стояли к моменту разлива.

### 4.5 Надёжность

- **Сторожевой таймер:** нет ни одного пакета 15 с → соединение рвётся.
- **Переподключение:** до 10 попыток подряд с паузой 3 с. Счётчик сбрасывается при каждом успешном входе.
- **Продолжение:** при разрыве после входа рассылка продолжается со следующей неотправленной команды (`sentIndex`), список не пересчитывается. Если всё уже отправлено — штатное завершение.
- **Смерть:** при health ≤ 0 бот сам отправляет respawn (в течение всего сеанса).
- Чат сервера логируется как `[chat] …` — там видны ответы на `/fill` (успех/ошибка).

### 4.6 Производительность (по реальным схемам, 5 команд/с)

| Схема | Блоков | Команд | Твёрдых | Крепящихся | Воды/лавы (боксами) | ≈ время |
|---|---|---|---|---|---|---|
| house.json | 688 | 82 | 72 | 10 | 0 | 16 с |
| ostankino.json | 2640 | 596 | 596 | 0 | 0 | 2 мин |
| npp-2.json | 8726 | 602 | 600 | 0 | 2 | 2 мин |
| npp-v3-2.json | 31537 | 1008 | 1006 | 0 | 2 | 3,5 мин |
| npp-final.json | 21192 | 1363 | 1313 | 42 | 8 | 4,5 мин |

Время растёт от числа команд, а не блоков: большие однородные объёмы дешёвые, пёстрый декор — дорогой (по одному `/setblock` в порядке файла).

Числа перемерены после исправления бага в `buildFillCommands` (см. §10.5.2 «Опыт»): раньше было `boxes.flatMap(splitBox)`, а `Array.flatMap` зовёт колбэк как `(element, index, array)` — индекс подставлялся в необязательный параметр `maxVolume` вместо `MAX_FILL_VOLUME`, из-за чего боксы с маленьким индексом резались до отдельных клеток, а с большим — не резались вовсе. Прежние значения в этой таблице (например, 1809 команд для `npp-v3-2.json`) были искажены этим багом.

**Второй пересчёт (см. §10.4.8 «Опыт»):** вода/лава больше не идут по одному `/setblock` в общем позднем проходе, а схлопываются в боксы отдельным финальным проходом (§4.4) — отсюда резкое падение числа команд у схем с водой: `npp-2.json` было 894 команды (294 из них — вода поштучно), стало 602 (2 бокса воды); `npp-v3-2.json` было 1300 (294 воды поштучно), стало 1008 (2 бокса); `npp-final.json` было 1632 (277 воды поштучно из 319 крепящихся — остальные 42 это двери/факелы), стало 1363 (42 крепящихся как раньше + 8 боксов воды). У `house.json`/`ostankino.json` воды нет, числа не изменились. Заодно твёрдые боксы теперь сортируются по нижней Y (снизу вверх) — на число команд не влияет, только на порядок отправки (см. §4.3).

### 4.7 Телепорт на площадку, зоны, учёт ответов, `--retry`

**Проблема, которую это решает** (см. §10.2.8 «Опыт», проверено на сервере): бот — сырой клиент без модели мира, сервер шлёт ему чанки только вокруг его РЕАЛЬНОЙ позиции. Если бот всё время стоял в другом месте (например, у точки входа), а схема строится далеко — часть команд уходит в незагруженные чанки и не встаёт, без явной ошибки в чате.

**Телепорт (`ensureSpectatorMode`/`teleportTo` в index-cmd.js).** После готовности (см. §4.2 п.4) и до первой команды схемы/`--wipe`/`--retry` (не для тестового режима без схемы — там площадки нет):
1. `/gamemode 3` (наблюдатель — полёт без коллизий, не упадёт и не задохнётся в толще камня). Подтверждение — пакет `game_state_change` с `reason=3`.
2. `/tp <ник> X Y Z` в центр габарита схемы (для `--wipe`/`--retry` — в центр их бокса/содержимого команд) на высоту `max(Y) + 10`. Подтверждение — пакет `position`. По протоколу 1.12.2 сервер после этого ждёт `teleport_confirm` с тем же `teleportId` — raw-клиент (в отличие от mineflayer) не шлёт его сам, поэтому `teleportTo` делает это явно.
3. Пауза `config.tpChunkLoadWaitMs` (5000 мс) — на догрузку чанков.

Если сервер не подтвердил `/gamemode 3` или `/tp` за 5 с — понятная ошибка и `exit 1` (похоже на отсутствие OP), а не тихое зависание.

**Зоны (`buildZonePlan`).** Габарит всех команд (X/Z, из самих строк `/fill`/`/setblock` — см. `computeCommandListBounds`) сравнивается с `config.tpRenderRadiusBlocks * 2` (дальность прорисовки от центра до края, по умолчанию 128 блоков — сервер не сообщает реальное значение по протоколу 1.12.2, так что это настраиваемая оценка, не измеренный факт). Если габарит больше — список команд группируется по зонам (сетка со стороной `tpRenderRadiusBlocks * 2`), **порядок команд внутри зоны сохраняется как в исходном списке** (стабильная группировка) — поэтому инварианты «твёрдые раньше крепящихся, крепящиеся в порядке файла» (§4.2, §4.4) не ломаются: у любой постройки её твёрдые и крепящиеся блоки лежат рядом в пространстве и почти наверняка попадают в одну и ту же зону. Перед каждой зоной — свой `/tp` в её центр (среднее из команд зоны) и та же пауза на догрузку. При разрыве соединения посреди зоны реконнект возобновляет ровно с той же зоны (по `sentIndex`), с новым `/tp` в неё.

**Учёт ответов сервера.** Ответы на `/fill`/`/setblock` приходят в чат как `{"translate":"commands.fill.success","with":[...]}` — без ключа-перевода, клиент без языкового файла не может (и не должен) сам его «озвучивать», но ключ и не нужен, чтобы классифицировать ответ. **Как именно сопоставлено** (сделано «в лоб», как и просили, — задача сама признаёт, что надёжного способа нет):
- каждая реально отправленная команда кладётся в FIFO (`pendingResponses`) в момент отправки;
- каждое входящее сообщение чата, чей `translate`-ключ начинается на `commands.` (значит это точно ответ на команду, а не случайная реплика), снимает **самую старую** команду из FIFO и присваивает ей этот ответ; сообщения без такого ключа (обычный текст) FIFO не трогают;
- это работает, только если во время стройки в чате не происходит ничего постороннего от других источников (другой игрок, посторонняя команда) — сообщения от них с `translate`, начинающимся на `commands.`, ошибочно «съедят» слот в очереди и сдвинут сопоставление для всех команд после. На выделенном сервере для одной стройки это не проблема; при параллельной активности — может быть.
- `commands.fill.success`, `commands.setblock.success` — успех; `commands.fill.failed`, `commands.setblock.noChange` — «без изменений» (уже стоит нужное или объём уже пуст/полон), не ошибка; любой другой ключ на `commands.` (например `commands.fill.outOfWorld`, `commands.generic.permission`) — ошибка; команда, на которую за 10 с после отправки последней команды в списке вообще не пришло ответа — тоже ошибка («нет ответа от сервера»), потому что при незагруженных чанках сервер иногда просто ничего не шлёт.

**Сводка и повтор.** В конце — строка вида `ИТОГ: N ответов - успешно A, без изменений B, ошибок C` и разбивка ошибок по ключам. Все команды-ошибки (включая «нет ответа») — в `logs/failed-<label>-<время>.txt` (одна на строку; `<label>` — имя схемы без `.json`, `wipe` или `retry-<имя файла>`), с готовой подсказкой команды повтора: `node index-cmd.js --retry logs/failed-....txt`. Повтор идёт той же логикой телепорта/зон/учёта — файл читается как обычный список команд.

**Логи.** Все `console.log`/`console.error` (значит, и `log()` из `lib/utils.js`) дублируются в `logs/<label>-<время>.log` (перехват `process.stdout.write`/`process.stderr.write` — не нужно искать и дублировать каждый вызов по отдельности). `logs/` — в `.gitignore`.

**Проверено на сервере:** `/fill` 3×3×3 `stone`, затем тем же объёмом `air` (через `--wipe` с `--ground` выше бокса для сплошного `stone`, и без `--ground` для сплошного `air`) — оба раза: первое подключение получило `ECONNRESET` (см. §10.2.1 «Опыт», это норма), второе прошло; `/gamemode 3` подтвердился ответом `{"translate":"gameMode.changed","with":[{"translate":"gameMode.spectator"}]}`; `/tp` — ответом `{"translate":"commands.tp.success.coordinates","with":["Builder","X.5","Y.0","Z.5"]}` (координаты сервер округляет к центру блока, отсюда `.5`); `/fill` — `{"translate":"commands.fill.success","with":["27"]}` (27 = 3×3×3). Сводка и файл логов отработали корректно.

## 5. Режим B — `index.js` (mineflayer, «в мире»)

> **На нашем сервере режим `index.js` (mineflayer) НЕ РАБОТАЕТ: mineflayer не разбирает чанки модовой сборки.** Сбой воспроизводился ещё при разработке бота: при приёме `map_chunk` пакеты не распаковываются (inflate) или приходят битыми, из-за чего внутренний парсер mineflayer падает ещё до того, как код бота получает управление (подробный разбор — §10.1, §10.3) — именно поэтому в проекте вообще появился `index-cmd.js` (протокол без модели мира). Код `index.js`/`lib/build.js`/`lib/commands.js` оставлен в репозитории как задокументированная (нерабочая на этом сервере) альтернатива, но использовать его нельзя. Любые задачи, которым нужна модель мира через mineflayer (чтение блоков, рельефа, `bot.blockAt` и т.п.), этим путём не решаются. Описание ниже (§5.1–§5.4) - это то, как режим устроен ПО КОДУ, а не подтверждённое рабочее поведение на этом сервере.

### 5.1 Запуск и жизненный цикл

`node index.js`. Первым подключается `lib/patch-items.js` (до mineflayer). На `login` бот только логирует версию; на `spawn` пишет в чат приветствие. При `end` — переподключение через `reconnectDelayMs`, без лимита попыток.

### 5.2 Чат-команды

| Команда | Действие |
|---|---|
| `!help` | список команд |
| `!goto X Y Z` | дойти до точки (pathfinder, радиус `gotoRangeBlocks`) |
| `!place X Y Z блок[:meta]` | поставить один блок |
| `!build файл.json X Y Z` | построить схему от origin X Y Z |
| `!stop` | сбросить цель pathfinder и флаг занятости |

Пока выполняется команда, остальные отклоняются («Занят…»), кроме `!help` и `!stop`.

### 5.3 Как ставится блок (`placeBlockAt`)

1. Если в точке уже нужный блок (имя + metadata) — пропуск. Если там твёрдый блок — ошибка «место занято» (**бот не ломает блоки**).
2. Подходит на расстояние `gotoRangeBlocks + 3`.
3. Ищет опору среди соседей в порядке: снизу, +X, −X, +Z, −Z, сверху. Нет опоры — ошибка.
4. Берёт материал в руку. В creative — кладёт `new Item(id блока, 64, metadata)` в первый слот хотбара (с кэшем, только при смене материала). В survival — ищет в инвентаре.
5. `bot.placeBlock` по грани опоры.

`!build` сортирует схему по Y (снизу вверх) и ставит по одному блоку с паузой 1,2 с. В чат — ошибка по каждому неудавшемуся блоку и итог.

### 5.4 Ограничения режима (почему он не для города)

- **Ориентация не соблюдается.** Ступеньки, двери, факелы и т.п. при установке рукой поворачиваются по взгляду бота, metadata схемы игнорируется. Проверка «уже стоит» для таких блоков будет расходиться с фактом *(по коду, не проверено на сервере)*.
- **Блоки, у которых id предмета ≠ id блока** (двери, вода, лава, таблички, редстоун и т.п.), выдать в руку не получится *(по коду, не проверено)*.
- **Модовые блоки** не поддерживаются: их нет в `minecraft-data`, ответ «неизвестный блок».
- `air` в схеме ничего не расчищает: в пустом месте — пропуск, в занятом — ошибка.
- Скорость: ~50 блоков/мин.

## 6. Формат JSON-схемы

### 6.1 Структура

```json
[
  { "x": 0, "y": 0, "z": 0, "block": "stonebrick" },
  { "x": 1, "y": 0, "z": 0, "block": "concrete:14" },
  { "x": 1, "y": 1, "z": 0, "block": "stone_brick_stairs:2" },
  { "x": 2, "y": 0, "z": 0, "block": "air" }
]
```

- Массив объектов. Обязательные поля: `x`, `y`, `z` (числа), `block` (строка). Лишние поля игнорируются.
- Координаты **относительные**, целые. Оси как в игре: **+X восток, +Z юг, +Y вверх**. Все существующие схемы начинаются с `(0,0,0)` и лежат в неотрицательных координатах — так и держать (поворот рассчитан на это).
- `y = 0` — уровень origin. Основание (`--foundation-to`) строится ниже него.
- Порядок элементов важен только для крепящихся блоков (§4.4). Для mineflayer-режима схема сортируется по Y.
- Дубликаты координат: в командном режиме побеждает последняя запись; в mineflayer — обе попытки.

### 6.2 Поле `block`

- `"имя"` → metadata 0; `"имя:N"` → metadata N (разбирается по **последнему** двоеточию, N — целое ≥ 0).
- Имена — **ванильные ID блоков 1.12.2** (`stonebrick`, `brick_block`, `planks`, `concrete`, `stained_glass`, `quartz_block`, `sea_lantern`…), не названия предметов и не «плоские» имена 1.13+ (`white_concrete` — **неверно**, надо `concrete:0`).
- Префикс `minecraft:` допустим.
- **`air`** — полноценный блок: в командном режиме заливается воздухом, так вырезают внутренние объёмы (в схемах АЭС до 2/3 записей — `air`).
- **Модовые блоки** в формате `"modid:name"` или `"modid:name:meta"` технически проходят разбор и попадут в `/setblock`/`/fill` как есть; сервер Forge должен их знать. *Не проверено на сервере; реестровые имена блоков AE2/IC2 надо уточнять (например, через F3 в игре).*

### 6.3 Валидация при загрузке

Проверяется только: массив, у каждого элемента числовые x/y/z и строковый block. **Не проверяется:** целочисленность координат, существование блока, допустимость metadata. Ошибки имён всплывут только в чате сервера (`[chat]` в логе).

Имя файла — только в папке `schemas/` (путь обрезается до имени).

### 6.4 Metadata направленных блоков 1.12.2 (справка)

| Блок | Значения |
|---|---|
| ступеньки `*_stairs` | 0 восток, 1 запад, 2 юг, 3 север; +4 = перевёрнутые |
| факел `torch` | 1 восток, 2 запад, 3 юг, 4 север (на стене, сторона крепления); 5 = на полу |
| кнопки, рычаг | стены как у факела 1–4; кнопка 0 потолок / 5 пол; рычаг 0,5,6,7 пол/потолок |
| `ladder`, `chest`, `furnace`… | 2 север, 3 юг, 4 запад, 5 восток |
| двери `*_door` | нижняя половина: 0 восток, 1 юг, 2 запад, 3 север (+4 открыта); верхняя: 8 (петля слева), 9 (петля справа) |
| брёвна `log`/`log2` | порода 0–3; +4 ось X (восток–запад), +8 ось Z (север–юг), +12 кора со всех сторон |
| `quartz_block` | 0 обычный, 1 резной, 2 колонна вертикальная, 3 колонна по X, 4 колонна по Z |
| плиты `*_slab` | +8 = верхняя половина |

Цвета (`concrete`, `wool`, `stained_glass`, `stained_hardened_clay`, `carpet`): 0 белый, 1 оранжевый, 2 пурпурный, 3 голубой, 4 жёлтый, 5 лаймовый, 6 розовый, 7 серый, 8 светло-серый, 9 бирюзовый, 10 фиолетовый, 11 синий, 12 коричневый, 13 зелёный, 14 красный, 15 чёрный.

## 7. Поворот (`--rotate`, `rotateSchema`)

- По часовой стрелке при взгляде сверху, Y не меняется. Габарит `SX = maxX+1`, `SZ = maxZ+1` считается от исходных координат.
- 90°: `x' = SZ−1−z`, `z' = x`; 180°: `x' = SX−1−x`, `z' = SZ−1−z`; 270°: `x' = z`, `z' = SX−1−x`. После поворота координаты сдвигаются так, чтобы минимум X и Z снова был 0 → **origin всегда остаётся углом с минимальными X/Z**.
- Metadata пересчитывается для: ступенек, факелов (в т.ч. редстоуновых), кнопок, рычага, `ladder`/`chest`/`trapped_chest`/`ender_chest`/`furnace`/`lit_furnace`, нижних половин дверей.
- **Не пересчитывается** (после поворота будут смотреть не туда):
  - таблички и рельсы — выводится предупреждение;
  - **брёвна и кварцевые колонны по X/Z** (ось должна меняться X↔Z при 90/270), **люки, калитки, раздатчики, воронки, наковальни, кровати, поршни, лианы** и прочие — без предупреждения.

## 8. Моды (AE2, IC2)

- Командный режим: модовые блоки теоретически ставятся по реестровому имени (§6.2). *Не проверено.*
- Режим mineflayer: не поддерживаются. `patch-items.js` лишь не даёт боту падать, когда сервер присылает неизвестные предметы (подменяет их на `unknown_<id>`).
- Имена модов в `isAttachedBlock`/повороте не учитываются: модовый блок всегда считается «твёрдым» и не поворачивается.

## 10. Опыт: что пробовали и почему отказались

Раздел-память. Цель — чтобы новые чаты и Claude Code не переигрывали уже
сыгранные партии. Каждый пункт: **факт → как проверено → вывод**.

### 10.1 mineflayer на модовой сборке

#### 10.1.1 Бот входит в мир и глохнет

**Факт.** Бот проходит Forge-рукопожатие, появляется в списке игроков, затем
перестаёт отвечать. Процесс не падает и не переподключается — приходится
убивать вручную.

**Как проверено [сервер].** В логе перед зависанием:
```
problem inflating chunk
TypeError: Cannot read properties of undefined (reading 'value')
    at Client.<anonymous> (mineflayer/lib/plugins/blocks.js:330:52)
```
Исключение брошено синхронно внутри стрима протокола
(`FullPacketParser._transform` → `Readable.push` → `emit`), поэтому оно **не
попадает** ни в `client.on('error')`, ни в `'end'`, ни в
`process.on('uncaughtException')`. Снаружи всё выглядит живым.

Это же самое (тот же файл, та же строка `blocks.js:330:52`, то же сообщение)
независимо воспроизведено ещё раз в этом репозитории при попытке запустить
`survey.js` на реальном сервере (см. журнал изменений, коммит с удалением
`survey.js`) — совпадение двух независимых прогонов подтверждает вывод.

**Вывод.** Чанки этой сборки mineflayer не разбирает. Починить патчем
`blocks.js` нельзя: после неудачной распаковки поток рассинхронизирован, и
парсер читает мусор дальше. Лечится только отказом от модели мира.

#### 10.1.2 Версия протокола — проверена и исключена

**Факт.** Была рабочая гипотеза, что `autoVersionForge` договаривается не на ту
версию, и «problem inflating chunk» — это поведение протокола 1.8 (где чанки
пакуются zlib отдельно), а не 1.12.2.

**Как проверено [сервер].** Логирование на событии `login`:
```
version=1.12.2 protocolVersion=340
```
Версия верная.

**Вывод.** Гипотеза мёртвая, **повторно не проверять**. Битые чанки приходят при
правильно согласованной версии — это несовместимость mineflayer со сборкой, а
не ошибка конфигурации.

Попутно выяснено [код] — **подтверждено** чтением исходников зависимостей:
- `client.protocolVersion` на клиенте `minecraft-protocol` **не существует** как
  собственное поле (значение уходит в `options.protocolVersion`, а не в сам
  клиент) — правильное поле для mineflayer-режима — `bot.protocolVersion`
  (число, ставит `mineflayer/lib/loader.js:129`). В `lib/connect-raw.js` этот же
  факт обойдён явно: клиент сохраняет ссылку на `options` в `client.rawOptions`
  именно затем, чтобы `client.rawOptions.protocolVersion` можно было прочитать
  снаружи (см. комментарий в файле).
- Логировать версию на `connect` бесполезно: это сырой TCP-коннект, ping, по
  которому `autoVersionForge` определяет версию, идёт параллельно и обычно не
  успевает. Самая ранняя точка — `login`.

#### 10.1.3 patch-items.js: работает, но лечит не то

**Факт.** AE2/IC2 добавляют предметы с id вне ванильного диапазона;
`prismarine-item` падает на них с `AssertionError: item with id NNNN not found`.

**Как проверено [сервер].** Патч отработал ровно как задумано: пять модовых id
(4246, 4152, 4139, 4137, 4138) залогированы по одному разу, заглушки
подставлены, падения нет.

**Вывод.** Патч нужен и работает, но это **отдельная** проблема от чанков.
После него бот всё равно умирает на `map_chunk`. Не путать эти два симптома.

### 10.2 Сервер и хостинг

#### 10.2.1 Anycast-прокси рвёт первое соединение

**Факт.** Первая попытка подключения регулярно получает `ECONNRESET` через
несколько секунд, вторая проходит штатно. Воспроизводится и на mineflayer, и на
командном режиме.

**Как проверено [сервер].** Многократно, на обоих режимах; независимо
воспроизведено ещё раз в этом репозитории при первой попытке запустить
`survey.js` (см. журнал изменений). Прокси — фильтрующий обратный прокси класса
TCPShield (Anycast от hosting-minecraft.pro), он разбирает пакет рукопожатия и
решает, пускать ли соединение.

**Вывод.** Автопереподключение — не роскошь, а обязательное условие.
Разрыв до `login` считать нормой и молча пробовать снова (уже реализовано,
см. §4.5).

#### 10.2.2 Порт и SRV

**Факт.** Прокси-домен работает без явного порта; прямой адрес требует порт.

**Как проверено [код].** Подтверждено чтением `minecraft-protocol/src/client/tcp_dns.js`:
`options.port = options.port || 25565` (порт по умолчанию), затем SRV-запрос
`_minecraft._tcp.<host>` делается **только если** `options.port === 25565` **и**
хост не IP и не `localhost`. При любом другом явном порте SRV пропускается.

**Вывод.** `MC_PORT` оставлять пустым при работе через прокси-домен. Ключ `port`
не передавать в `createBot`/`createClient` вообще, а не передавать `undefined`
(так и сделано в `lib/connect.js`/`lib/connect-raw.js`: `hasExplicitPort` решает,
добавлять ли ключ `port` в `options`, а не что в него положить).

#### 10.2.3 Права

**Факт.** Без OP команды не проходят: сервер отвечает
`{"translate":"commands.generic.permission"}` в чат.

**Как проверено [сервер].** Первый успешный тест командного режима упёрся ровно
в это: соединение держалось, команда ушла, сервер ответил отказом.

**Вывод.** `/op <ник бота>` — обязательный шаг настройки. Ник в конфиге и ник,
которому выдан OP, должны совпадать (наступали на это при переименовании
`AI` → `Builder`).

#### 10.2.4 Лимит `/fill`

**Факт.** Ванильный лимит — 32768 блоков на команду.

**Как проверено [сервер + код].** Консоль при ручной зачистке:
```
Too many blocks in the specified area (38955 > 32768)
```
Подтверждено и в коде: `lib/fill-plan.js` явно называет 32768 протокольным
лимитом 1.12.2 (32×32×32) и использует его напрямую для `--wipe`
(`WIPE_MAX_FILL_VOLUME` в `index-cmd.js`).

**Вывод.** Любой расчёт объёма зачистки считать заранее. Для площадки
36×52 это максимум 17 слоёв по Y на команду (36×52=1872, 32768÷1872≈17,5).

#### 10.2.5 `/fill` воздухом в пустоту

**Факт.** Если `/fill … air` не меняет ни одного блока, сервер отвечает
`{"color":"red","translate":"commands.fill.failed"}`. Команда безвредна, но:
поток красных строк в чате выглядит как сбой, и **на сервере ничего не
происходит визуально**.

**Как проверено [сервер].** Это стоило нескольких ложных диагнозов «бот завис».
Симптом: команды в консоли бота идут, на сервере тишина. Разгадка подтвердилась,
когда уровень `--ground` подняли на блок и постройка пошла.

**Вывод.** Отсутствие видимых изменений ≠ зависание. Перед тем как искать
проблему в соединении, проверить, не уходят ли команды в уже пустой объём.
(Добавлено в §11 «Известные проблемы».)

#### 10.2.6 Мёртвый игрок остаётся мёртвым

**Факт.** Игрок, отключившийся мёртвым, при следующем входе оказывается мёртвым
снова. Обычный клиент показывает экран смерти; сырой клиент висит в нём вечно,
потому что не шлёт пакет возрождения.

**Как проверено [сервер].** Симптом: бот входит, часть команд ещё проходит,
потом сервер перестаёт их принимать, а бот ничего не замечает.

**Вывод [уже реализовано, см. §4.5].** Слушать `update_health`, при `health <= 0`
слать `client_command` с `actionId: 0`. Очередь команд не стартовать, пока не
получен первый `position` или `update_health` с health > 0. Это ровно то, что
делает текущий `index-cmd.js` — пункт не устарел, а зафиксирован как уже
закрытый.

#### 10.2.7 Длина сообщения в чате

**Факт [код].** Лимит чат-пакета в 1.12 — 256 символов. Команды длиннее не
отправляются.

**Как проверено [код].** `MAX_CHAT_LENGTH = 256` в `index-cmd.js`, проверка в
`createCommandQueue.enqueue` — совпадает дословно.

**Вывод.** Для `/fill` и `/setblock` запас огромный, но проверка в очереди
оставлена на случай длинных модовых имён.

#### 10.2.8 Команды в незагруженные чанки не выполняются

**Факт [сервер, проверено].** Схема `embankment-1-earthworks.json` отработала
частично: команды из второй половины списка (расчистка `air`, вода, парапет)
встали, а первые (массивы камня/песчаника/каменного кирпича) — нет.

**Как проверено [сервер].** Гипотеза: бот — сырой клиент без модели мира и без
физики, он никогда не шлёт свои `position`-пакеты и не переставляет себя ничем,
кроме `/tp`; сервер грузит чанки клиенту вокруг его РЕАЛЬНОЙ последней позиции
(сохранённой в player-файле с прошлого входа), а не там, где стоится схема. Раз
бот всё время фактически стоял в другом месте, часть команд ушла в незагруженные
чанки. Проверено добавлением явного `/gamemode 3` + `/tp` в центр площадки перед
стройкой (см. §4.7) — после этого на живом сервере прогнан тестовый `/fill`
3×3×3 `stone`, затем тем же объёмом `air`: оба раза `/tp` подтвердился
(`commands.tp.success.coordinates`), `/fill` — успехом (`commands.fill.success`,
`with:["27"]`). Отдельно от воспроизведения самой поломки (её не пересоздавали
намеренно, чтобы не портить рельеф участка ещё раз) — это подтверждает, что
телепорт-перед-стройкой работает, а не что именно телепорт был единственной
причиной случившегося: конкретный `commands.*.outOfWorld`/аналогичный ответ на
не вставшие команды той стройки в чате не сохранился, поэтому первопричина
(именно недогруженные чанки, а не что-то ещё) - **гипотеза, не факт**, несмотря
на то, что сам механизм телепорта проверен и работает.

**Вывод.** Бот без модели мира должен сам телепортироваться на участок перед
стройкой, а не полагаться на то, что сервер и так пришлёт нужные чанки — теперь
это часть конвейера (§4.2 п.5, §4.7), а не отдельный шаг оператора.

### 10.3 Почему командный режим

**Факт.** `index-cmd.js` — сырой `minecraft-protocol` + `minecraft-protocol-forge`,
без mineflayer и без модели мира.

**Как проверено [сервер].** Контрольный тест: подключение → 60 секунд простоя →
`/setblock` → ещё 15 секунд наблюдения. Связь не отвалилась,
`inflate`-ошибка не появилась вообще.

**Почему это работает [код, подтверждено].** В этом режиме **ноль слушателей** на
`map_chunk` и прочих world-пакетах — проверено построчно: в `index-cmd.js` и
`lib/connect-raw.js` единственные `client.on(...)` — это `packet` (только метка
времени для сторожевого таймера), `error`, `kicked`, `end`, `chat`,
`update_health`, `position`. Ни один не читает содержимое чанков. Даже если
сервер шлёт битый чанк, `minecraft-protocol` молча роняет пакет в слое сжатия
(`compression.js`: `catch` без `throw`, просто `cb()`), а обработчиков, которые
могли бы упасть на его разборе, в этом режиме просто нет.

**Вывод.** Для всего, что не требует читать мир, это единственный рабочий путь.
Новых mineflayer-режимов не добавлять (см. CLAUDE.md).

### 10.4 Схемы и генерация

Пункты 10.4.1–10.4.7 описывают практику подготовки схем **вне этого
репозитория** (генератор и валидаторы не входят в код mc-bot — схемы
готовятся отдельно и кладутся в `schemas/`, см. TODO §11.8). Код здесь
сверить не с чем; выводы приняты как задокументированная практика.

#### 10.4.1 «Полость» обязана быть явным воздухом

**Факт.** Если генератор просто *не кладёт* блок в объём комнаты, там остаётся
исходный грунт.

**Как проверено [сервер].** Первая АЭС: тоннели, шахты и дверные проёмы оказались
забиты землёй, потому что расчистка (`--clear-above`) не доставала до подземной
части. Под стеклом бассейна вместо шахты был виден грунт.

**Вывод [подтверждено кодом].** Все внутренние объёмы задавать записями
`"block": "air"`. `air` — полноценный блок для командного режима (§6.2). В
схемах АЭС воздух — до двух третей записей: `npp-final.json` 13 835 из 21 192,
`npp-v3-2.json` 21 481 из 31 537 (см. §9) — числа совпадают с «до двух третей».

#### 10.4.2 Порядок в генераторе: кто позже, тот и прав

**Факт.** В генераторе схема собирается в словарь по координате, и любая более
поздняя запись затирает раннюю.

**Как проверено [сервер + расчёт].** Наступали многократно:
- цоколь, построенный сплошной заливкой вместо оболочки, залил **весь первый
  этаж** бетоном на два блока — все проёмы превратились в щели;
- коридор, прокопанный после лестницы, **стёр нижние ступени**;
- площадка у подножия лестницы **заложила кирпичом кусок коридора**;
- массив лестницы **перекрыл** магистральный коридор.

**Вывод.** Жёсткий порядок слоёв в генераторе (продублировано в §12 «Правила
для проектирования схем»):
1. массивы (все короба стен и грунта),
2. расчистка всех полостей,
3. восстановление полостей, которые расчистка соседей могла задеть,
4. **ступени, декор и мелочь — последними**.

#### 10.4.3 Проверять геометрию кодом, а не глазами

**Факт.** Визуальная проверка эскиза не ловит непроходимость.

**Как проверено [сервер].** Три версии АЭС подряд уехали на сервер с
непроходимыми лестницами и проёмами. После введения валидатора такие ошибки
находились до отправки.

**Вывод.** Два обязательных прогона перед выдачей схемы (продублировано в §12):
- **валидатор проходимости** — BFS «игроком» высотой 2 блока от точки входа до
  контрольного списка мест. Клетка проходима, если под ногами твёрдо, а на
  уровне головы и ног пусто. Не тронутое схемой считать твёрдым **ниже** уровня
  земли и воздухом **выше**. Учитывать как проходимые: двери, стремянки,
  кнопки, рычаги, нажимные плиты, воду; уметь лазить по `ladder`.
- **валидатор опор** — у каждого крепящегося блока проверить блок, к которому он
  крепится (по metadata), у стоящих на полу — блок снизу. Целевое значение — ноль
  висящих.

#### 10.4.4 Эргономика лестниц

**Факт [сервер].** Что выяснилось опытным путём:
- **Просвет над ступенью — 4 блока**, не 3. При трёх голова упирается в потолок
  следующей ступени: пройти можно, но некомфортно.
- **Блоки-ступеньки** (`*_stairs`), а не полные блоки: полушаг вместо шага.
- Марш должен **начинаться на уровне пола и кончаться на уровне пола**. Ступень,
  совпавшая с полом коридора, выглядит как утопленная в пол яма.
- Верхняя ступень должна примыкать к целому полу, иначе к лестнице не подойти —
  спуск оказывается ямой, а не лестницей.
- Марш в 3 блока шириной, упирающийся в коридор шириной 1 — тупик. **Коридоры
  делать шириной 3.**
- Если техничка должна быть закрытой — тамбур со стенами и потолком **на всю
  длину проёма в полу**, иначе в него сваливаются сбоку мимо двери.

#### 10.4.5 Двери, кнопки, плиты

**Факт [сервер].**
- **На `iron_bars` не встают ни двери, ни кнопки.** Проём ворот делать сплошной
  стеной, решётку оставлять только на прогонах ограды. (Добавлено в §11
  «Известные проблемы».)
- **Кнопка без metadata** — это metadata 0 = потолочное крепление (см. §6.4),
  ей нужен блок **сверху**. Поставленная на стол кнопка висит в воздухе и
  отваливается. Согласуется с кодом: `recalcMetadataForRotation` в
  `lib/fill-plan.js` трактует 0 как «потолок» для кнопок (см. §7).
- **Нажимные плиты удобнее кнопок** на проходных дверях: наступил — открылось.
  Бонус: у плит нет направленной metadata, поворот схемы их не ломает
  (`stone_pressure_plate`/`wooden_pressure_plate` действительно отсутствуют в
  списках `recalcMetadataForRotation` — подтверждено кодом).
- **Крепящиеся блоки обязаны идти поздним проходом**, иначе ставятся раньше
  своей опоры и осыпаются. Внутри позднего прохода порядок из файла сохранять
  строго: нижняя половина двери раньше верхней. Уже реализовано (§4.4).

#### 10.4.6 Вода

**Факт [сервер].** Вода должна отправляться после готовых бортов, иначе
разливается. Уже реализовано: `water`/`lava` идут последним проходом,
отдельно от всех остальных крепящихся блоков (§4.4) — с исправления
из §10.4.8 они ещё и не по блоку, а боксами.

**Отдельно:** стремянка, доведённая до слоя стеклянного дна бассейна, **заменяет
стекло собой**, и бассейн течёт. Проверять, что направленные блоки не попадают в
слои, которые должны остаться целыми.

#### 10.4.7 Чего бот не может в принципе

**Факт [код].** `/setblock` ставит только блоки. Не получится:
- **картины и стойки для брони** — это сущности, нужен `/summon`;
- **таблички с текстом** — текст живёт в NBT, `/setblock` его не передаёт.

**Вывод.** Такой декор в схемы не закладывать; либо отдельная механика
(`/summon`, `/setblock` с NBT-аргументом) — не реализована. (Добавлено в §11
«Известные проблемы».)

#### 10.4.8 Падающие блоки и порядок боксов

**Факт [сервер, наблюдалось; причина подтверждена моделированием].** Песок в
схемах `embankment-1b-beach.json` и `embankment-1c-beach-natural.json` падал
при постройке — на сервере после стройки вместо ровного пляжа оказалась
непредсказуемая каша из осыпавшегося песка, а не форма с превью.

**Как проверено.** Обе итоговые схемы (как множества клеток) были провалидированы
до отправки обоими обязательными валидаторами (§12) — проходимость и опоры —
и оба были чистыми. Валидаторы проверяют только **итоговое состояние**
(«песок в конце стоит на твёрдом»), а не порядок, в котором клетки реально
встают на сервере. `buildFillCommands` до этого исправления мёржил твёрдые
клетки в боксы и отправлял их **в порядке первой клетки в файле** (§4.3 до
правки) — а не снизу вверх. Из-за этого бокс песка нередко уходил раньше
бокса каменного ядра под ним: в момент установки песка опоры ещё не было
(там воздух или вода), и он падал как обычный гравитационный блок. Прямое
моделирование по фактическому списку команд подтвердило причину: `1b` — песок
без опоры в 734 колоннах в старом порядке, `1c` — в 726; при сортировке тех
же боксов по нижней Y (без изменения самих боксов, только порядка отправки) —
0 в обеих схемах.

**Вывод [исправлено кодом].** `buildBoxes` в `buildFillCommands` (`lib/fill-plan.js`)
теперь сортирует итоговые боксы по нижней Y бокса по возрастанию — стабильно,
при равной Y порядок как в файле (см. §4.3). Применяется и к твёрдым блокам,
и (отдельно) к воде/лаве — они всё ещё идут финальным проходом, после
крепящихся, но внутри себя тоже снизу вверх (§4.4). Итоговое состояние не
меняется (боксы не пересекаются) — меняется только физика по ходу стройки.
Добавлена самопроверка порядка (`checkFallingSupport`, см. §12): для каждой
падающей клетки схемы (`sand`, `gravel`, `concrete_powder`, `anvil`,
`dragon_egg`), если клетка под ней тоже есть в схеме, требуется, чтобы она
была твёрдой (не вода/лава, не крепящийся блок) и её бокс шёл строго раньше
(или это один и тот же бокс — тогда обе клетки уходят одной командой
одновременно). Нарушения печатаются в лог с координатами (`index-cmd.js`).
Важная оговорка: **валидатор итогового состояния (§10.4.3) в принципе не
может поймать проблему порядка** — оба валидатора смотрели именно на то, что
получится, если бы всё уже стояло разом, что и произошло в 1b/1c формально
верно (там, где падал не весь столбец, а первый слой) — реальный источник
дефекта был не в форме, а в последовательности установки; нужна отдельная
проверка именно порядка (сделано выше).

### 10.5 Схлопывание и производительность

#### 10.5.1 Ложная тревога про мёрж

**Факт.** Было подозрение, что `buildBoxes` схлопывает только по Y: в логе шли
команды вида `/fill 191 64 288 191 70 288` — колонки 1×7×1.

**Как проверено [расчёт, подтверждено кодом].** Написана независимая эталонная
реализация того же жадного алгоритма. На `npp-v3-2.json` (31 537 записей) она
дала **1008 боксов**; при повторной проверке сейчас `buildBoxes(schema)` на том
же файле по-прежнему даёт ровно 1008. Через полный конвейер
(`buildFillCommands`, где крепящиеся блоки вынимаются до мёржа) — 1006 боксов.
Совпадение точное.

**Вывод.** Мёрж исправен, **гипотезу не переигрывать**. Колонок 1×N×1 в этой
схеме 223 из тысячи — это вертикальные рёбра фасада, трубы и детали шириной в
блок. Схлопывать там нечего.

#### 10.5.2 `maxFillVolume` = 4096

**Факт [гипотеза].** Значение выбрано как предосторожность: большие `/fill`
предположительно подвешивают модовый сервер, а подвисший сервер не отвечает на
keep-alive.

**Что известно точно [расчёт, перепроверено].** На `npp-v3-2.json` крупнейший
бокс после мёржа — **1479 блоков**. То есть на реальных схемах лимит 4096
**не срабатывает ни разу** и на число команд не влияет.

**Вывод.** Утверждение в §3.2 BOT.md, что большие `/fill` подвешивают сервер,
**на нашем сервере не проверялось** — формулировка в §3.2 исправлена, теперь
явно названа предосторожностью, а не измеренным фактом.

**Найдено при добавлении этого раздела [код, БАГ, исправлено].** Во время
проверки чисел из этого пункта обнаружилось, что таблица производительности в
§4.6 не совпадала с независимо измеренным здесь числом боксов (1809 команд для
`npp-v3-2.json` в таблице против 1006–1008 боксов по расчёту). Причина — реальный
баг, не просто устаревшая документация: `buildFillCommands` вызывал
`boxes.flatMap(splitBox)`, а `Array.prototype.flatMap` зовёт колбэк как
`(element, index, array)`. У `splitBox(box, maxVolume = MAX_FILL_VOLUME)`
второй параметр необязательный — но `index` не равен `undefined`, поэтому
дефолт `MAX_FILL_VOLUME` никогда не срабатывал: боксу с индексом 0 доставался
лимит `0` (резался до отдельных клеток), боксу с индексом 4096 — лимит 4096
(случайно верный), боксу с индексом больше того — лимит **больше** протокольных
32768 (не резался бы вовсе, с риском получить от сервера `Too many blocks`,
см. §10.2.4). Баг введён вместе с `--wipe` (тогда `splitBox` получил
необязательный параметр `maxVolume` для переиспользования с другим лимитом) и
жил в коде до этого раздела. Исправлено на `boxes.flatMap((box) => splitBox(box))`;
таблица в §4.6 пересчитана по факту.

#### 10.5.3 `commandsPerSecond` = 5

**Факт [гипотеза].** Порог подобран на глаз. Кик при темпе 5/с ни разу не был
однозначно привязан к темпу: все расследованные случаи объяснились другими
причинами (§10.1.1, §10.2.1, §10.2.5, §10.2.6).

**Вывод.** Считать настраиваемым параметром, а не константой из измерения. Ванильный
антиспам чата ОПов не касается, так что запас, скорее всего, есть.

## 12. Правила для проектирования схем под город

- Строить **командным режимом** (`index-cmd.js`), боту дать OP.
- Держать схемы в неотрицательных координатах от `(0,0,0)`, `y=0` — уровень пола/земли.
- Только ванильные имена 1.12.2 с metadata (§6.2, §6.4). Модовые — только после проверки на сервере.
- Интерьерные пустоты задавать явными `air`, чтобы `--prepare` не был обязательным.
- Если здание будет ставиться с поворотом — избегать брёвен/колонн по X/Z и направленных блоков вне списка §7, либо проектировать сразу в нужной ориентации.
- Крупные однородные массивы выгоднее: время стройки зависит от числа команд (§4.6).
- **Жёсткий порядок слоёв в генераторе схемы** (см. §10.4.2 «Опыт» — источник большинства геометрических провалов проекта): 1) массивы (короба стен и грунта); 2) расчистка всех полостей; 3) восстановление полостей, которые расчистка соседей могла задеть; 4) ступени, декор и мелочь — последними.
- **Перед отправкой на сервер — три обязательных прогона** (валидаторы проходимости и опор — см. §10.4.3 «Опыт», валидатор порядка постройки — см. §10.4.8 «Опыт», добавлен после падения песка в схемах 1b/1c района «Набережная»):
  1. **валидатор проходимости** — BFS «игроком» высотой 2 блока от входа до контрольных точек; двери/стремянки/кнопки/рычаги/нажимные плиты/вода — проходимы, `ladder` — можно карабкаться;
  2. **валидатор опор** — у каждого крепящегося блока — опора по metadata; у стоящих на полу — блок снизу; цель — ноль висящих. Оба валидатора выше смотрят только на **итоговое** состояние схемы — они не ловят проблемы порядка установки (см. следующий пункт);
  3. **валидатор порядка постройки** (`checkFallingSupport` в `lib/fill-plan.js`, встроен в `buildFillCommands` — отдельно вызывать не нужно, но если генератор схемы работает вне этого репозитория, эквивалентную проверку надо повторить у себя): каждый падающий блок (`sand`, `gravel`, `concrete_powder`, `anvil`, `dragon_egg`) в момент установки должен иметь твёрдую опору — либо из самой схемы (более ранний по порядку отправки блок), либо из известного рельефа (клетки нет в схеме — считается, что опора там уже есть на местности). Цель — ноль нарушений.

  В ответ на генерацию схемы включать результат всех трёх проверок.
